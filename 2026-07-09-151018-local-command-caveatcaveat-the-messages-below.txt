  ---
  Audit: Two Issues

  1. Preview rendering too slow (not Fiji-level)

  Root cause: No tracking cache between /preview calls. Every Z-scrub re-walks
  the entire chain from seed_frame to target_frame from scratch.

  The target_frame fix was correct — it stopped walking the full bidirectional
  113 frames. But scrubbing to frame 80 from seed at frame 50 still walks 30
  frames, each running segment_slice_seeded, which does:
  - Gaussian blur
  - Otsu threshold
  - Connected component labeling + fill holes
  - Contour extraction
  - And in the worst case, 9 attempts per frame (3 center positions x 3 radii,
  lines 488-514 of seeded_vesicle.py)
  - Plus a random_walker fallback (_try_rw_ws_in_disk) which is expensive scipy

  So frame 80 = ~30 frames x up to 9 calls = ~270 segmentations per scrub. There
  is zero caching between requests — app.py:356 creates a fresh
  track_seeded_vesicle_stack call every time.

  Why Fiji is instant: Fiji doesn't segment on scrub. It shows the raw image
  with an OvalRoi overlay. LimeSeg runs the fitting once as a separate batch
  operation, not per-frame on scrub.

  Fix direction: Cache the tracking results keyed by (stack_id_or_path, seed_x, 
  seed_y, seed_frame, seed_radius). On scrub to frame N+1, only compute one more
  frame instead of re-walking from scratch. The handoff called this out
  explicitly (priority #2).

  2. Green ROI goes blank after some frames

  Root cause: Tracking genuinely loses the vesicle. This is not a UI bug — it's
  the segmentation failing at difficult Z planes. When sres.ok is False,
  app.py:437-465 draws an empty overlay (just the seed marker, no green
  contour).

  The tracking fails because of cascading issues in propagate()
  (seeded_vesicle.py:477-527):

  1. Fixed ref_area from equator: ref_area = max(first.area_px, 1.0) (line 471)
  is the seed-frame area. At the poles of a GUV, the cross-section shrinks well
  below 0.25 * ref_area, hitting the min_area_ratio gate (line 505). This is
  geometrically correct — polar slices of a sphere really do shrink — but the
  gate doesn't adapt.
  2. Otsu failure on weak slices: _adaptive_threshold_sparse uses Otsu on pixels
  inside the disk. At weak-signal Z planes (near vesicle poles), there's not
  enough membrane signal to separate from background, so either everything is
  foreground or nothing is.
  3. Gap-then-drift: After a gap frame, cx, cy stays at the last good center
  (line 521: the continue skips the cx, cy = res.center_xy update). If the
  vesicle is floating laterally through Z, the search center doesn't track the
  drift through gaps, making subsequent recovery harder.
  4. RW fallback area gate: Even the _try_rw_ws_in_disk random walker fallback
  has its own area rejection (ref_area * 0.2 to ref_area * 2.5, line 401), which
  compounds with the same fixed-ref problem.

  This matches bugs #9 and #11 from the handoff, both marked "Partial". The
  tracking works for the first several frames where the cross-section is near
  the equator, then drops out as it approaches the poles.

  Fix direction:
  - Adaptive ref_area: update the reference area as you walk (rolling average or
  gradual decay toward current slice area) instead of locking to seed frame
  - More forgiving area gates at the extremes (allow smaller fractions at high Z
  distance from seed)
  - After gaps, extrapolate the center drift direction instead of holding
  position
  - The Polar-DP approach from the Gemini research (handoff priority #4) would
  sidestep this entirely for near-round GUVs

  ---
  Summary: The two issues are related but separate. Speed needs a tracking cache
  so scrub doesn't re-walk from scratch. The blank ROI is the tracking
  algorithm genuinely losing the vesicle at challenging Z planes due to rigid
  area gates and fixed reference area. Both need code changes, but the cache is
  lower risk / higher payoff for daily use, while the tracking robustness is the
  harder CV problem.

  Critical

  1. Percentile threshold fallback is unreachable (seeded_vesicle.py): The new
  percentile fallback for weak signals is inside the except Exception block of
  the Otsu call. But Otsu succeeds on nearly all non-uniform images — it just
  returns a bad threshold. So the fallback never fires when it's actually needed
  (weak signal where Otsu merges FG/BG). It needs to be a post-Otsu quality 
  check (e.g., "if >90% of disk pixels pass the Otsu threshold, try percentile
  instead"), not an exception handler.
  2. Upload preview cache key uses temp path (app.py:972): The /upload/preview
  endpoint builds stack_identity from stack.source_path, which is a random temp

  session stack_id or uploaded filename hash instead.

  Moderate

  3. Center extrapolation doesn't scale with gap duration (seeded_vesicle.py):
  When extrapolating through a multi-frame gap, dx/dy is applied once regardless
  of how many frames were skipped. A 3-frame gap should extrapolate 3x the
  step, not 1x.
  4. recent_centers ignores frame gaps (seeded_vesicle.py, extend_track): The
  velocity calculation uses adjacent entries in recent_centers without checking
  if they came from adjacent Z-frames. Non-adjacent frames give wrong velocity
  estimates.
